## 1. Aroma Profile — circular/leaky label disclosure

**Suggested placement:** Evaluation/Results chapter, immediately after you
report the Aroma Profile classifier's accuracy figure. Also reference it
briefly in Limitations.

> The Aroma Profile classifier reports near-perfect accuracy (99.9–100% across
> both the held-out test split and 5-fold cross-validation). This figure must
> be interpreted with caution and is disclosed here as a methodological
> limitation rather than presented as evidence of real-world predictive
> power. No publicly available dataset pairs UCI-style wine physicochemical
> measurements with independently verified sensory/aroma-panel labels.
> Because of this, the Aroma Profile label used for training was generated by
> a deterministic rule (`01_data_preparation.py`) applied directly to four of
> the same physicochemical features — residual sugar, citric acid, volatile
> acidity, and alcohol — that are also supplied to the model as predictors.
> The classifier is therefore not predicting an independent, human-verified
> outcome; it is recovering a fixed mathematical function of its own inputs,
> which is a form of circular (data-leakage) evaluation. A near-100% score is
> the expected result of this setup and should not be read as evidence that
> the system can predict genuine human-perceived aroma. The four other
> outputs (Quality Score, Quality Range, Price Range, Consumer Segment) do
> not share this specific issue in the same way, though Price Range and
> Consumer Segment labels are likewise rule-derived rather than
> independently collected (see Limitation 1 above). A genuine fix would
> require either a real sensory panel dataset or an aroma label derived from
> an independent source not used as a model input — for example, text-mined
> aroma descriptors from a wine-review corpus (see the related Kaggle Wine
> Reviews discussion below), which was outside the time budget of this
> project and is proposed as future work.

## 2. Node.js and Kaggle Wine Reviews — proposal-vs-implementation reconciliation

**Suggested placement:** Methodology chapter, in the section introducing the
technology stack and datasets, immediately after (or replacing) the
sentence(s) that list "React, Flask, Node.js, MongoDB" and "UCI Wine Quality
+ Kaggle Wine Reviews".

> The Project Proposal and Contextual Report describe the intended technology
> stack as React, Flask, Node.js, and MongoDB, and the intended data sources
> as the UCI Wine Quality dataset combined with the Kaggle Wine Reviews
> dataset. Two adjustments were made during implementation and are disclosed
> here explicitly. First, no standalone Node.js/Express backend service was
> built. Node.js is present in the system only as the JavaScript runtime
> that powers the React frontend's build tooling (the `npm`/Create React App
> development server and production bundler); all server-side logic —
> prediction, authentication, role-based access control, admin approval, and
> the chatbot — is implemented in a single Flask (Python) service that
> communicates with MongoDB directly via the `pymongo` driver. This is a
> deliberate architectural simplification (one backend service instead of
> two) rather than an oversight, and is disclosed here so the report does not
> imply a Node.js API layer exists where it does not. Second, the Kaggle
> Wine Reviews dataset was not used in final model training; only the UCI
> Wine Quality dataset (red and white variants merged, `01_data_preparation.py`)
> was used. This decision was made because the two candidate datasets do not
> share a reliable common key at the individual-wine level — UCI Wine
> Quality contains physicochemical lab measurements with no wine
> name/producer/vintage identifiers, while Kaggle Wine Reviews contains
> reviewer text, price, and named wines with no physicochemical measurements
> — so the two cannot be joined at the row level without fabricating a
> mapping between them. Combining them would have required either
> discarding the physicochemical grounding that makes the quality-prediction
> models defensible, or inventing a join that has no basis in the data,
> neither of which was judged acceptable. A legitimate future-work direction
> is proposed instead: using the Kaggle Wine Reviews text corpus for a
> separate, independent NLP-based aroma/price signal (e.g. sentiment or
> keyword extraction from review text) that does not depend on a row-level
> join to the UCI data, which would also address the Aroma Profile
> circularity issue described above by supplying an aroma label that is not
> derived from the same physicochemical inputs the model predicts from.

### Why both matter for the viva

An examiner who has read the Proposal and Contextual Report closely may ask
directly: *"Where is the Node.js component?"* or *"Did you actually use the
Kaggle dataset you proposed?"* Having these paragraphs already written and
in the report — rather than having to explain the discrepancy for the first
time verbally under questioning — turns a potential credibility problem into
a demonstration of methodological rigor and honest scope management, which
examiners consistently reward more than a system that silently over-claims.
